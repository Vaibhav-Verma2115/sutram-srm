Sutram SRM — Product Documentation Set

Deep Learning Super-Resolution Mapping from Medium-Resolution Satellite Imagery. Sentinel-2 10 m → 2.5 m with per-pixel trust.

Team Sutram · Smart India Hackathon · Generated 24 August 2026 · Contains: PRD · SRS · System Architecture · UI/UX Specification · Development Plan

What this system is, in one paragraph Sentinel-2 gives free, frequently-updated imagery of all of India at 10 m per pixel — good enough to see a field, not good enough to see its boundary. Sutram SRM uses generative deep learning to reconstruct that imagery at 2.5 m, and — critically — ships a per-pixel confidence map alongside it, so an analyst always knows which sharpened details are supported by the sensor data and which the model inferred. It is a super-resolution system that tells you when not to trust it.

1. Product Requirements Document

1.1 Problem statement

Medium-resolution satellite imagery (10–30 m) is the backbone of operational Earth observation in India: it is free, covers the whole country, and refreshes every five days. But at 10 m a village road is one pixel wide, a small building is sub-pixel, and a field boundary is a blur. Analysts in agriculture, urban planning and disaster response therefore face a hard choice:

OptionCostConsequence
Use free 10 m imageryFree, national coverage, 5-day revisit Cannot resolve the features the decision actually depends on
Buy commercial sub-metre imageryThousands of rupees per scene Unaffordable at state or national scale; infrequent revisit

Generative super-resolution promises a third option — but introduces a new and serious problem. A model that sharpens imagery is also a model that can invent imagery. An analyst shown a crisp building that the sensor never observed may make a real decision on a fabricated pixel. This risk, not image quality, is the reason super-resolution is not already operational in most agencies.

The problem we are actually solving Not “make satellite images sharper” — several open models already do that. The unsolved problem is making super-resolved imagery trustworthy enough to act on: producing enhanced imagery together with a defensible, validated statement of which pixels are supported by observation and which are model inference.

1.5 MVP scope

The MVP is deliberately narrow: F1–F6 only, RGB+NIR bands, on pre-downloaded scenes.

In MVPDeferred, and why
4 bands (B04, B03, B02, B08) at ×4 20 m red-edge/SWIR bands — doubles data engineering for marginal demo value
Manually downloaded Sentinel-2 scenes In-app AOI fetch — adds an external API dependency that can fail during a live demo
Single-user local application Accounts, roles, multi-tenancy — no second user exists yet
Precomputed products in the demo Live inference in-app — LDSR takes ~100 s/tile; unacceptable interactively
Streamlit UI Custom React frontend — would consume the whole build budget for no added capability
Explicit anti-scope No user accounts, no database, no cloud deployment, no mobile app, no real-time processing, no multi-sensor support in the MVP. Each of these is a plausible future feature and none of them help the system produce a trustworthy super-resolved pixel, which is the entire point.

1.8 Assumptions

  • Sentinel-2 L2A remains freely available through the Copernicus Data Space.
  • The ×4 degradation operator is approximately scale-invariant, so a model trained at 20 m → 5 m transfers to 10 m → 2.5 m.
  • SEN2VENuS same-day pairs are co-registered well enough to train on without further alignment.
  • Users have a GIS tool (QGIS is free) for consuming GeoTIFF output.
  • A human reviews outputs before any operational decision.

1.9 Risks

RiskImpactMitigation
Model hallucinates plausible but false structuresHigh Trust layer with four independent signals; validated calibration; confidence band shipped inside the product file

Diffusion branch too slow for interactive useMedium Precompute demo products; fidelity branch runs in 40 ms for interactive paths

Model underperforms on terrain unlike training dataMedium Multi-site training; confidence map degrades gracefully and flags the shortfall
Upstream package churn (stale checkpoint URLs)Low Pinned fetch scripts; already encountered and handled once

1.10 Acceptance criteria

  1. Given a valid 4-band Sentinel-2 GeoTIFF, the system outputs a 6-band COG at exactly ¼ the pixel size with identical bounds and CRS.
  2. Bands 5 and 6 of every output contain sigma and confidence respectively.
  3. Every branch is benchmarked on the same tile with PSNR, SSIM, SAM and ERGAS reported.
  4. The calibration curve shows mean error decreasing as confidence increases.
  5. The demo application runs with no network connection and displays imagery, confidence, NDVI and metrics.
  6. Training can be interrupted and resumed with no loss beyond the current epoch.
  7. All documentation regenerates from source.

2. Software Requirements Specification

2.1 Scope and interpretation

A note on shape This is a scientific data-processing system, not a transactional web application. Requirement areas that a standard SRS template emphasises — accounts, roles, permissions, session management — are deliberately minimal in the MVP, because the MVP has exactly one user class operating a local tool. They are specified here for the deployed service variant so the design does not have to be retrofitted later, and each is marked with the release it applies to.

2.2 User roles and permissions

2.3 Functional requirements

Ingestion and preprocessing

IDRequirementAcceptance test
FR-1Accept a GeoTIFF with exactly 4 bands in order B04, B03, B02, B08 A 3-band or 5-band input is rejected with a message naming the expected order
FR-2Convert integer L2A DN to 0–1 reflectance on request (--reflectance) Input with max DN 10000 yields max reflectance 1.0
FR-3Clip reflectance to [0,1]; negative values from atmospheric correction are removedNo output pixel is negative
FR-4Mask SCL classes 0, 1, 3, 8, 9, 10 when an SCL band is supplied, before super-resolution; record the masked fraction Verified — --scl masks 22.9% of a test scene to exactly 0.0; metrics.json carries cloud_fraction
FR-5Tile inputs of arbitrary size into 128×128 with 32 px overlap A 1000×700 non-square input produces correct 4000×2800 output
FR-6Blend overlapping tiles with a Hann window No visible seam along tile boundaries in the output

Super-resolution

IDRequirementAcceptance test
FR-7Provide four selectable branches: bicubic, SEN2SR, LDSR-S2, Ours --branches accepts any comma-separated subset
FR-8All branches expose predict(lr) -> Prediction A new branch is usable with no change to pipeline or evaluation code
FR-9Upscale by exactly ×4 128×128 input yields 512×512 output
FR-10LDSR-S2 produces a per-pixel sigma from N stochastic samples With --n-samples 8, sigma is non-zero and varies spatially
FR-11Support CPU, Apple MPS and CUDA Identical output shape on all three; MPS materially faster than CPU

Trust layer

IDRequirementAcceptance test
FR-12Compute LR-consistency by PSF-downsampling the SR output and differencing against the inputBicubic scores worse than the hard-constrained branch
FR-13Compute per-pixel spectral angle between input and downsampled output Output is in degrees, finite everywhere
FR-14Compute branch disagreement as normalised difference Zero when both branches agree; bounded in [0,1]
FR-15Fuse available signals into confidence in [0,1] No value outside range; missing signals reweight rather than fail
FR-16Report ΔNDVI introduced by super-resolution Mean |ΔNDVI| below 0.01 for the fidelity branch

Output and validation

IDRequirementAcceptance test
FR-17Write a 6-band COG: 4 SR bands, sigma, confidence gdalinfo reports 6 bands with named descriptions and overviews
FR-18Preserve CRS exactly and rescale the transform so bounds are unchanged Bound drift = 0.0 m; pixel size exactly ¼ of input
FR-19Verify footprint after every write and record the result Metrics JSON contains a footprint.ok field
FR-20Implement Wald's protocol with PSF-based degradation Degradation is not bicubic; documented and configurable
FR-21Report PSNR, SSIM, SAM, ERGAS, RMSE per branch All five present in benchmark.json
FR-22Produce a calibration curve binding confidence to observed error Correlation reported; bins include pixel counts

Training

IDRequirementAcceptance test
FR-23Download SEN2VENuS sites with resume support An interrupted download continues from its byte offset
FR-24Pack patches into float16 shards, streamed not buffered Peak memory independent of site size
FR-25Support ×2 (native) and ×4 (PSF-degraded input) pairing modes Manifest records which mode produced the shards
FR-26Filter patches on contrast, not zero-fraction Dark-biome sites yield a non-zero usable count
FR-27Checkpoint every epoch and resume model, optimiser, scaler and epoch Kill mid-run; resumed loss continues the prior trajectory
FR-28Optimise L1 + LR-consistency + SAM + gradient with configurable weights Each term is logged separately per epoch

2.4 Business rules

IDRuleRationale
BR-1No super-resolved product may be written without a confidence band Prevents downstream use of sharpened pixels stripped of their caveat
BR-2Geospatial footprint must never change A shifted product silently corrupts every overlay analysis built on it
BR-3Reflectance is never rescaled for aesthetics Contrast stretching is display-only; analysis consumes physical values
BR-4Cloud-flagged pixels are masked before, not after, super-resolution Super-resolving cloud produces convincing, meaningless texture
BR-5Generative-branch output is labelled visual-grade, not analysis-grade Measured: it is the least LR-consistent branch
BR-6Every published metric states its protocol and reference PSNR without a stated degradation is unfalsifiable

2.9 Security requirements

  • No credentials in the repository. Copernicus access is interactive; no API keys are stored.
  • Model provenance is pinned. Weights are fetched from named repositories at explicit paths and verified by size; a silently substituted model is a supply-chain risk for a system whose output informs decisions.
  • Checkpoints are loaded from trusted paths only. PyTorch deserialisation executes code; loading an untrusted .pt is remote code execution.
  • Uploaded rasters are treated as untrusted input — validated for band count, CRS and size before any processing.
  • v2 service: TLS in transit, encryption at rest, per-user product isolation, audit log of every job submission and download.

3. System Architecture Document

3.1 Architectural principles

Deliberately not a microservice platform The MVP is a Python library with a thin UI. There is no database, no message queue, no container orchestration and no API gateway, because there is no requirement that needs them: one user, local files, batch processing. Every component below earns its place by serving a stated requirement. The v2 service design is included so the boundaries are right from the start — but it is explicitly not built yet.
  • Files are the interface. GeoTIFF in, COG out. Any GIS tool, any language, no client library required.
  • One interface for all models. Adding a branch touches no other component.
  • Uncertainty travels with the data, inside the same file, not in a sidecar that can be lost.
  • Everything regenerates from source — products, metrics and documentation.

The production quality signal LR-consistency is the architecturally important metric: it compares the product against its own input, so it runs on every real scene where no ground truth exists. It is the difference between a system that was validated once and a system that reports its own health continuously.

4. UI/UX Specification

4.1 Design principles

PrincipleWhat it means here
Uncertainty is not an advanced feature Confidence is surfaced on the main screen, not buried in a settings panel. The whole product claim depends on it being seen.
The comparison is the interface A super-resolved image alone means nothing. Every view shows before and after together.
Never let a demo depend on the network The app reads precomputed products. No model call, no download, no API during a presentation.
Honest visuals Contrast stretching is labelled display-only. The UI never makes output look better than the data supports.
No decoration No splash screens, no animation, no gradients. Every pixel of chrome competes with the imagery the user came to see.

4.8 Accessibility

  • Never colour alone. Low-confidence regions carry a numeric percentage caption as well as the red overlay — essential given red/green colour-vision deficiency affects roughly 8% of men.
  • Body text contrast ≥ 4.5:1; the primary colour on white measures ~8.6:1.
  • All controls keyboard reachable; the threshold slider is arrow-key adjustable.
  • Every image carries a descriptive caption stating resolution and content.
  • Metric tables are real tables with headers, not images — screen-reader navigable.
  • Confidence rendered as greyscale intensity, legible without colour perception.

How to state this honestly Our model achieves the best structural (SSIM) and spectral (SAM) fidelity of the three branches, trading raw PSNR for the properties that matter in remote sensing — which is exactly what its loss function optimises. It does not beat SEN2SR on PSNR or ERGAS, and we do not claim it does.

Two caveats to state before a reviewer raises them. First, this evaluation tile is European, while our model was trained only on Indian terrain (KUDALIAR) — it is being tested out-of-domain and still leads on two of four metrics. Second, PSNR is a per-pixel L2 measure and is well known to correlate weakly with interpretability; SSIM and SAM are the metrics a remote-sensing reviewer weighs. On its own KUDALIAR validation split the model reaches 39.23 dB PSNR and 0.9524 SSIM.
